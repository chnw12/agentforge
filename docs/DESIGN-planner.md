# 계획 도우미(Planner) 설계

> 상태: **구현 완료 (M1~M5)**. 아래 3.11의 결정이 반영되었고, 구현 결과와 검증은 README와 테스트(`test/planner*.test.ts`)를 참고하세요. 이 문서는 설계 당시의 근거를 보존합니다. 각 항목은 **[관찰]**(직접 확인한 사실), **[설계]**(이 문서의 제안), **[미확인]**으로 구분합니다.

## 1. 요구사항 (요청 원문 정리)

1. 화면 옆에 **대시보드(패널)**를 둔다.
2. 사용자가 **Codex / Claude Code 중 하나를 골라** 쓴다. (당장은 이 둘만)
3. 사용자가 **작업 결과를 복사·붙여넣기**하면, 그 에이전트가 **다음 작업을 설계**해 준다.
4. 설계가 나오면 **"새 태스크를 만들까요?"**를 묻는다.
5. "만들기"를 누르면 **새 태스크에서 작업이 이어진다.**

### 2.1 사례 요약

### 2.2 가장 가까운 사례와 결론
- **UX는 Amp handoff**가 가장 가깝습니다: *목표를 말한다 → AI가 초안 프롬프트를 만든다 → 사람이 고쳐서 보낸다.*
- **구조는 Orchestrator.inc**를 참고할 만합니다: 계획 에이전트는 "조율만 하고 구현은 하지 않는다"는 역할 분리, 워커마다 읽기 쉬운 이름 라벨(`--name`, 100자 이하), 워커→오케스트레이터 보고 채널(`ao report`).
- **Superset의 완료 봉투**는 "결과를 구조화해 다음 작업의 입력으로 쓴다"는 점에서 컨텍스트 형식에 참고가 됩니다.
- 이 요청처럼 **"사람이 결과를 붙여넣고, 에이전트(Claude/Codex 선택)가 설계하고, 사람이 확정해야 새 태스크가 생기는"** 조합은 조사한 범위에서는 그대로 있는 사례를 찾지 못했습니다 [미확인: 조사 범위 한정].
- 핵심 차별점: Orchestrator.inc는 **자동 위임**, 우리는 **사람 승인 게이트 유지**. 이는 AgentForge의 기존 원칙(머지·단계 실행은 항상 사용자 클릭)과 맞습니다.

### 2.3 rea 분석 결과 (Orchestrator.inc v0.14.2 Windows 설치 파일)
설치 파일(NSIS)을 `7z`로 풀어 `resources/daemon/ao.exe`와 `resources/app.asar`를 분석했습니다. 받은 코드는 읽기만 하고 실행하지 않았습니다.

| 대상 | 도구 | 관찰 |
|---|---|---|
| `daemon/ao.exe` | `inspect_go_binary` (증거 `ev_48864dbb…bc5`) | Go 1.27.1, 모듈 `…/backend/cmd/ao`, 의존성: `coder/acp-go-sdk`(Agent Client Protocol), `modernc.org/sqlite`, `goose`, `chi`, `cobra`, `rrule-go`(스케줄). **LLM SDK는 없음** → 에이전트는 CLI/ACP로 구동 |

| `daemon/ao.exe` 문자열 | **rea가 아닌 단순 바이트 검색** | 오케스트레이터 역할 프롬프트(`human-facing orchestrator for project`), `ao spawn --project`, `ao report` 등이 **배포 바이너리에 그대로 존재** (소스와 일치) |

소스(오픈소스)에서 읽은 내용 [관찰]:
- 오케스트레이터 = **`sessionRole="orchestrator"`인 일반 채팅 세션**이다. 별도 "계획 화면"이 아니다.
- 역할 프롬프트(`backend/internal/session_manager/prompt.go`): "구현은 하지 말고 조율만, 구현 작업은 항상 워커를 스폰하거나 재지시", "복잡한 계획은 짧은 계획부터 작성", "스폰 전 현재 상태를 점검해 중복 방지", "명시적 제한(local-only 등)은 워커에 그대로 전달".
- 워커는 `ao report`로 오케스트레이터에 체크포인트·완료 보고(산출물 첨부 가능).

**rea 분석의 한계** [미확인]
- Ghidra가 설정되어 있지 않아 네이티브 문자열 검색·역컴파일은 불가했습니다. 그래서 문자열 확인은 바이트 검색으로 대체했습니다.
- asar 의미 그래프는 결과 크기 제한으로 **부분 커버리지**입니다(미확인 관계가 4만 건 이상). 오케스트레이터 UI의 실제 흐름은 rea가 아니라 공개 소스로 확인했습니다.
- 도중 `close_binary`가 세션의 보관 증거를 지워 추적(`trace_application_feature`)이 한 번 실패했고, 범위를 좁혀 다시 분석했지만 이 청크만으로는 흐름 정보를 얻지 못했습니다.

## 3. 설계

### 3.1 사용자 흐름
```
① 태스크에서 결과를 확인한다 (예: Best-of-N 슬롯 요약, 파이프라인 검증 결과)
② [계획 도우미에 추가] 버튼 → 패널의 "컨텍스트"에 요약이 들어간다   (또는 직접 붙여넣기)
③ 에이전트(Claude Code | Codex)를 고르고 "다음에 하고 싶은 일"을 한 줄 적는다 → [설계 요청]
④ 에이전트가 읽기 전용으로 저장소를 살펴보고 "제안 카드"를 돌려준다
   (제목 · 모드 추천 · 요청 내용 초안 · 근거/위험/확인할 점)
⑤ 사용자는 카드를 읽고 고른다
     [새 태스크 만들기]  →  새 태스크 창이 미리 채워져 열림 → 사용자가 확인 후 [생성]
     [계속 논의]         →  같은 스레드에서 추가 질문/수정 요청
     [닫기]              →  아무것도 만들지 않음
⑥ 새 태스크는 "계획 출처"가 기록되고, 평소처럼 파이프라인/Best-of-N으로 진행된다
⑦ 그 결과를 다시 ②로 보내 다음 설계를 이어간다 (루프)
```

### 3.3 데이터 모델 (`src/shared/types.ts` 확장)
```ts
export interface PlanContextItem {
  id: string
  label: string                      // 예: "슬롯 1 (Claude Code) 요약"
  kind: 'paste' | 'slot' | 'stage' | 'task'
  text: string                       // 추가 시점의 스냅샷 (원본 태스크가 삭제돼도 유지)
  source?: { taskId: string; slotId?: string; stage?: StageKind }
  truncated?: boolean
}
export interface PlanProposal {
  title: string                      // ≤ 120자 (task:create 제한과 동일)
  prompt: string                     // ≤ 20,000자, 자체 완결형
  mode: TaskMode                     // 'pipeline' | 'best-of-n'
  slotAgents?: AgentKind[]           // best-of-n일 때 2~3개
  rationale?: string; risks?: string[]; questions?: string[]
}
export interface PlanMessage {
  id: string; role: 'user' | 'agent'; agent: AgentKind; text: string
  status: 'running' | 'done' | 'failed' | 'cancelled' | 'interrupted'
  proposal?: PlanProposal; proposalError?: string
  createdTaskIds: string[]           // 이 제안으로 만든 태스크
  createdAt: number
}
export interface PlanThread {
  id: string; projectId: string; title: string
  agent: AgentKind                   // 마지막으로 선택한 에이전트(메시지마다 바꿀 수 있음)
  contexts: PlanContextItem[]; messages: PlanMessage[]; createdAt: number
}
// Task에 추가:  origin?: { threadId: string; messageId: string; fromTaskId?: string }
// AppState에 추가: planners: PlanThread[]   (store.ts 로드 시 기본값 [])
```

### 3.4 컨텍스트 다이제스트 (순수 함수, `src/shared/planner.ts`)
"붙여넣기"가 번거롭지 않게, 이미 화면에 있는 정보를 **사실 위주**로 요약한다. 기본값은 **diff 본문 제외**(파일 목록과 +/−만), 필요하면 체크박스로 포함. [설계]
```
[슬롯 1 · Claude Code · 완료 · 테스트 PASS 3/3 · 파일 4 · +65 −1 · 42초]
변경 파일: work_claude.txt(+1 −0), …
요약(에이전트 최종 답변):
<slot.output 앞부분, 최대 N자>
```
- 항목당 최대 30,000자, 전체 100,000자(설정으로 조정). 초과분은 **잘렸다고 표시**(`truncated`).

### 3.5 실행 방식 (`src/main/planner.ts`, 기존 패턴 재사용)
- **읽기 전용**으로 실행한다. 기존 설계 단계와 같은 플래그를 쓴다. [관찰: `pipeline.ts`]
  - Claude: `claudeArgs('design', settings)` → `-p --output-format stream-json --verbose --no-session-persistence [--safe-mode] --tools Read,Grep,Glob`
  - Codex: `exec --json --ephemeral --sandbox read-only -C <project> -o <outFile> [-m model] -`
- 작업 디렉터리는 프로젝트의 **메인 체크아웃**(읽기 전용). worktree는 만들지 않는다.
- 프롬프트는 stdin으로 전달. 스레드당 동시에 1회 실행(`active` 맵, `bestofn.ts`와 같은 방식), 타임아웃은 설정의 단계 타임아웃, [중지] 지원.
- 프로세스는 일회성이므로 **대화 이어가기는 이전 대화를 매번 다시 보내는 방식**(최근 N턴 + 컨텍스트)으로 한다. 세션 재개(`--resume`)는 쓰지 않는다(현재 `--no-session-persistence` 정책 유지).
- 프롬프트 골격 [설계]:
```

너는 계획 도우미다. 구현하지 말고, 다음 작업을 설계해 제안만 한다.
저장소는 읽기 전용으로 확인할 수 있다. 파일을 수정하거나 명령을 실행하지 않는다.

<goal>

<<<ITEM 1: 슬롯 1 요약>>> … <<<END>>>
…

…

- 출력 파싱: **마지막** `af-proposal` 펜스 블록만 JSON으로 파싱하고 검증한다(제목 120자, 요청 20,000자, `mode` 허용값, `slotAgents` 2~3개·`claude|codex`). 실패하면 제안 카드를 만들지 않고 원문과 오류를 보여주며 **"텍스트를 새 태스크 요청으로 가져오기"**를 제공한다. 출력은 **실행하지 않는다**.

### 3.6 제안 → 새 태스크 (사람이 확정)
1. [새 태스크 만들기] → 기존 `NewTask` 모달을 **미리 채운 상태**로 연다(`initial: { title, prompt, mode, slotAgents }` 프롭 추가). 사용자는 내용을 고치고 [생성]을 눌러야 한다. **원클릭 자동 생성은 두지 않는다.**
2. 생성 시 `task:create` 입력에 `origin`을 포함한다. 서버는 `threadId/messageId` 존재를 검증하고 `Task.origin`에 저장, 해당 메시지의 `createdTaskIds`에 추가한다.
3. 새 태스크 헤더에 **"계획 출처: <스레드 제목> ↗"**를 표시하고(클릭하면 패널에서 해당 메시지로 이동), 사이드바 행은 기존과 같다.
4. 같은 제안으로 이미 태스크를 만들었다면 "이미 만들었음"을 표시하고 다시 만들 때 확인한다.
5. 새 태스크는 **기존 흐름 그대로**(파이프라인 단계 승인 / Best-of-N 실행·선택·머지) 진행된다. 계획 도우미는 어떤 단계도 자동 실행하지 않는다.

### 3.7 API (IPC, `preload` 허용 목록에 추가)
`planner:list` · `planner:create(projectId, title?)` · `planner:delete` · `planner:addContext(threadId, item)` · `planner:removeContext` · `planner:send(threadId, text, agent)` · `planner:cancel(threadId)` · 로그 스트림 이벤트 `planner:log`. 모든 입력은 기존 핸들러처럼 ID 형식(8자리 hex)·길이·타입을 검증한다.

### 3.8 보안·프라이버시
| 위험 | 대응 [설계] |
|---|---|
| **붙여넣은 텍스트 속 프롬프트 주입**(에이전트 출력, 웹 내용 등) | 컨텍스트를 구분자로 감싸 "데이터"로 명시, 에이전트는 **읽기 전용**이라 직접 피해 없음. 단 제안의 `prompt`가 이후 **쓰기 권한이 있는 에이전트의 입력**이 되므로, 카드에 요청 내용 전문을 **편집 가능하게 표시**하고 사람이 확정해야만 태스크가 만들어진다 |
| **비밀 정보 유출** | 전송 전에 기존 `redact()`를 컨텍스트와 목표에 적용하고, 가린 개수를 UI에 알린다 |
| **외부 AI로 전송** | 패널 첫 사용 시와 설정에서 켜고 끌 수 있는 경고 배너("붙여넣은 내용과 저장소 일부가 Anthropic/OpenAI로 전송됩니다", README의 'AI 사용 시 주의사항' 링크). 개인정보·기밀을 붙여넣지 않도록 안내 |
| 과도한 크기 | 항목·전체 길이 상한과 잘림 표시, 제어문자 제거 |
| 에이전트가 파일을 바꿈 | 읽기 전용 플래그만 사용(Claude `--tools Read,Grep,Glob`, Codex `--sandbox read-only`). 단, 읽기 전용 샌드박스는 저장소 밖 파일 읽기까지 막지는 않을 수 있다 [미확인] — 기존 설계·검증 단계와 같은 한계 |
| 자동 확산 | 자동 태스크 생성·자동 실행 없음. 사람의 클릭이 항상 게이트 |

### 3.9 오류·경계 사례
- 선택한 CLI가 없거나 로그인 안 됨 → 에이전트 선택을 비활성화하고 이유 표시(`cliInfo` 재사용).
- 실행 중 앱 종료 → 메시지 `interrupted`로 복구, 프로세스는 기존 `killAll`에 포함.
- 프로젝트 제거 → 스레드는 보존하되 "프로젝트 없음" 표시, 제안으로 새 태스크 생성은 비활성.
- 원본 태스크 삭제 → 컨텍스트는 스냅샷이라 영향 없음. `origin.fromTaskId` 링크만 비활성.
- 제안 JSON 형식 오류, 여러 블록, 빈 응답 → 3.5의 실패 경로.
- 에이전트 응답 중 같은 스레드로 다시 요청 → 거부("이미 실행 중").
- 한글 입력(IME): 팔레트와 같은 원칙 — 단축키는 `e.code`, Enter 조합 확정은 `isComposing`으로 무시.

### 3.10 구현 단계 (제안)
| 단계 | 내용 | 규모 | 검증 |
|---|---|---|---|
| M1 | 타입·저장(`planners` 기본값, 마이그레이션) + 순수 로직(`shared/planner.ts`: 다이제스트 생성, 프롬프트 생성, 제안 파서/검증, 길이·잘림) | 작음 | 단위 테스트(파서: 정상/깨진 JSON/여러 블록/주입 문구/경계 길이) |
| M2 | `main/planner.ts` 실행기 + IPC + 취소/타임아웃/복구 | 중간 | 기존 **가짜 에이전트**에 "제안 블록을 출력" 모드를 추가해 Claude/Codex 양쪽 통합 테스트 |
| M3 | 패널 UI(스레드, 컨텍스트, 에이전트 선택, 전송/중지, 제안 카드) | 중간 | 실제 앱 E2E 스위트에 F 추가 |
| M4 | 새 태스크 연결(`NewTask` 미리 채움, `origin`, 출처 링크) + "계획 도우미에 추가" 버튼 | 중간 | E2E: 결과 추가 → 설계 → 생성 → 출처 표시 → 루프 |
| M5 | 마무리: `Ctrl+J`, 팔레트 항목, 알림, README·AI 주의사항·노티스 갱신 | 작음 | 기존 A–E 스위트 회귀 통과 |

테스트 원칙: 실제 `claude`/`codex`를 쓰지 않고 가짜 에이전트로 자동화하며, 실행 전에 PATH가 가짜를 가리키는지 확인한다(이번 세션에서 얻은 교훈).

### 3.12 (이전) 열린 질문 — 위 결정으로 대체됨
1. **패널 위치**: 오른쪽 접이식 패널(제안) vs 별도 전체 화면 탭?
2. **컨텍스트 기본값**: diff 본문은 기본 제외(제안)로 괜찮은지? 민감정보가 diff에 많이 들어갈 수 있어 기본 제외를 권장.

4. **모드 추천**: 에이전트가 파이프라인/Best-of-N을 추천하게 할지, 사용자가 항상 직접 고르게 할지?
